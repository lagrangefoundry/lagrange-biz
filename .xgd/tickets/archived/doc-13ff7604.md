# XGD Distribution, Identity and Licensing Architecture

## Objectives

- Distribute XGD to users with minimal setup friction
- Authenticate users via GitHub (no separate account required)
- Enforce licensing based on repo visibility (public = free, private = paid)
- Enable auto-update from the field
- Provide a customer support channel usable by both humans and XGD agents
- Protect proprietary prompts and system logic from casual inspection
- Allow closed beta with comped licenses before charging is introduced

---

## Guiding Principles

- GitHub is the single identity provider — no XGD-specific login
- All server-side secrets (Jira, license server, Paddle) live in the Cloudflare Worker — never shipped in the client
- The Cloudflare Worker is the single trusted broker for all server interactions
- Beta exercises the full production code path — license validation, private repo entitlement, T&C recording — just without charges
- Obfuscation and standalone binary distribution are pre-launch hardening, not beta blockers

---

## Components

### 1. GitHub App (Identity and Repo Access)

XGD uses a GitHub App (not OAuth) as the identity and repo access layer.

**Why GitHub App over OAuth:**
- Scoped installation tokens for repo push (every 2 minutes)
- Can read repo visibility (public/private) — the license gate
- Installation ID + repo URL = canonical device identity
- Revocable per-installation

**Setup flow:**
1. `xgd setup` detects if `gh` CLI is authenticated (reduces friction)
2. Opens browser to GitHub App installation URL (pre-filled with their repo)
3. User clicks one "Install" button
4. GitHub redirects to `localhost` callback (xgd spins a short-lived local HTTP server)
5. xgd captures `installation_id`, closes local server, continues setup

**Identity payload captured at install:**
- GitHub user ID (numeric, canonical)
- GitHub login (display name)
- Email (if available)
- Repo URL + visibility (public/private)

### 2. Registration and Onboarding

#### Beta: GitHub Handle Allowlist

During closed beta, access is controlled by an allowlist of GitHub user IDs stored in the Cloudflare Worker (KV store or Worker env). The user must be on the allowlist before activation succeeds.

- Martin manages the allowlist directly via Cloudflare dashboard or a thin admin CLI
- Allowlist entries: `{ github_user_id, github_login, added_date, notes }`
- Activation returns a clear error for unrecognised users: "XGD is currently in closed beta — contact [email] to request access"

#### Production: Open Registration

Remove the allowlist check. Any GitHub user can activate. License tier is determined by repo visibility (see §5).

---

### 3. T&Cs Acceptance

- Shown in CLI or dashboard on first run, before any other action
- User must explicitly accept (keypress or click — no implicit acceptance)
- Acceptance recorded server-side in Worker KV: `{ github_user_id, tc_version, accepted_at, repo_url, ip_hint }`
- T&C version is embedded in the activation token
- If T&Cs change, old tokens fail version check on next refresh — re-acceptance prompted in dashboard

---

### 4. Activation Flow (Cloudflare Worker: `/activate`)

```
Client                        Worker                         GitHub API    Keygen
------                        ------                         ----------    ------
POST /activate
  { github_installation_token,
    repo_url,
    xgd_version,
    tc_version_accepted }
                              Verify token with GitHub ──────────────────>
                              Get repo visibility ────────────────────────>
                              Check allowlist (beta only)
                              Record T&C acceptance
                              Create or retrieve Keygen license ───────────────────>
                              Issue signed activation JWT
                                { github_user_id,
                                  tier: free|pro|beta_pro,
                                  status: active|payment_at_risk|suspended,
                                  repo_url,
                                  tc_version,
                                  exp: now+24h }
<── activation JWT
```

Token is refreshed automatically with each push. If the token has less than 1 hour remaining, the push client requests a refresh inline.

### 5. Licensing

#### License Server: Keygen.sh

Keygen.sh is used as the license management layer. It is API-first, supports comped/trial licenses (no payment required), and integrates with Paddle for automated license creation on payment events.

**Why Keygen over Paddle-only:**
- Licenses exist as first-class objects independent of payments
- Beta comped licenses require no payment processor
- Adding Paddle later requires no rework: Paddle webhooks → Worker → Keygen

#### License Tiers

| Tier | Condition | Charge |
|---|---|---|
| `free` | Public GitHub repo | None |
| `pro` | Private GitHub repo + active Paddle subscription | Paid |
| `beta_pro` | Beta allowlist member | Comped, no charge |

#### Repo Visibility Gate

- Checked at activation and at every token refresh (i.e., every ~24h or on push)
- If a `free` user's repo goes private: activation returns `upgrade_required`; push is blocked; dashboard shows upgrade prompt
- If a `pro` user's payment fails: 7-day grace period (`status=payment_at_risk`), then `status=suspended`

#### Beta Behaviour

- All beta users receive `beta_pro` tier licenses regardless of repo visibility
- Enforcement code runs but does not block (public/private check executes, result is logged, gate is bypassed for `beta_pro`)
- This exercises the full production code path during beta

### 6. Payments: Paddle

Paddle is used as the payment and subscription processor.

**Why Paddle:**
- White-label hosted checkout (no Paddle branding required)
- Handles global VAT/tax as Merchant of Record
- Supports coupons and discount schemes (e.g., 50% off first year)
- Supports seat-based team plans (future)
- Mature dunning workflows for payment failure handling

**Beta:** Paddle is not integrated. Beta users receive comped Keygen licenses created manually.

**Production payment flow:**
```
User clicks "Upgrade" in dashboard
→ Opens Paddle hosted checkout (new tab, Phase 1)
→ Payment complete → Paddle webhook → Worker → Keygen license activated
→ Next token refresh → tier=pro
```

**Downgrade flow:**
```
Subscription cancelled or payment failed
→ Paddle webhook → Worker updates Keygen license status
→ 7-day grace: status=payment_at_risk, push continues, warning shown
→ Day 7: status=suspended, push blocked, dashboard shows fix-payment prompt
→ User fixes payment → Paddle webhook → status restored immediately
```

**Discounts:** Paddle coupon system. Time-limited percentage discounts (e.g., "50% off for 12 months") distributed via invite or campaign codes.

**Future: In-dashboard checkout (Phase 2):** Replace hosted checkout with Paddle's embedded checkout within the XGD dashboard.

### 7. Auto-Update

**Beta distribution:** pip package via GitHub Releases. Trusted users, no obfuscation required.

**Production distribution:** Standalone binary (Nuitka-compiled) via shell installer and Homebrew tap. pip retained as developer/secondary channel.

**Update mechanism:**
- On startup, xgd calls Worker `/releases/latest` (requires valid activation token — unregistered installs cannot fetch updates)
- Response: `{ latest_version, min_required_version, release_notes_url, download_url }`
- If `current < latest`: dashboard shows update banner; `xgd update` command applies update
- If `current < min_required`: xgd refuses to run until updated (security patch path)

**Beta auto-update:** `xgd update` runs `pip install --force-reinstall --no-deps <github-release-url>`.

**Production auto-update (binary):**
1. Download binary to temp path
2. Verify signature against embedded XGD public key
3. Atomic replace of current binary
4. Signal restart

**Binary signing:**
- macOS: Apple Developer ID + notarization (required for Gatekeeper)
- Linux: GPG-signed releases, public key hosted on `xgd.ai` domain
- PyPI: PEP 740 attestations via GitHub Actions OIDC (trusted publisher)

### 8. Cloudflare Worker (Single Broker)

All server-side logic lives in a single Cloudflare Worker. No other backend infrastructure required.

| Endpoint | Purpose |
|---|---|
| `POST /activate` | GitHub token → license check → activation JWT |
| `POST /tc/accept` | Record T&C acceptance |
| `GET /license` | Refresh/validate activation token |
| `GET /releases/latest` | Version check (requires valid token) |
| `GET /releases/:version` | Binary download (requires valid token) |
| `POST /support/tickets` | Submit bug or feature request → Jira |
| `GET /support/tickets` | List user's support tickets from Jira |
| `GET /support/tickets/:id` | Get ticket detail and status |
| `POST /support/tickets/:id/comments` | Add comment |

Worker KV stores:
- T&C acceptance records
- Beta allowlist
- Per-user last-seen metadata

Jira API key, Keygen API key, and Paddle webhook secret never leave the Worker.

### 9. Support System

See DOC-975 for full detail. Summary:

- Dashboard support tab (submit bug, submit feature request, view tickets, view status, add comments)
- Cloudflare Worker validates GitHub identity, brokers all Jira interactions
- No Jira account required for users
- Both humans and XGD agents can submit via the same endpoint (agent submissions include: xgd run ID, workflow identifier, repo info, failure details)
- XGD engineering tickets remain a separate internal system

**Beta requirement:** Basic support tab must be live at beta launch. Minimum: submit bug, submit feature request, view my tickets.

### 10. Obfuscation (Post-Beta)

**Goal:** Make prompts and system logic hard to extract from a distributed binary.

**Approach:**
1. Nuitka-compiled standalone binary — no .py files, compiled to C, no bytecode to inspect
2. Prompts compiled into binary as encrypted bundle
3. Bundle decryption key derived from the activation token — prompts cannot be decrypted without a valid registered license
4. Since xgd requires ongoing connectivity (push every 2 min), token is always fresh; no need for long-lived local key storage

**Beta:** Not applied. Trusted users, pip distribution.

---

### 11. Team / Org Licensing (Future)

Not included in initial launch. Architecture accommodates it:

- Cloudflare Worker identity model includes `github_org_id` field from day one (nullable, unused initially)
- Team tier: one Paddle subscription per GitHub org, covers up to N members (per-org seat-cap model)
- Org admin is the Paddle billing contact
- Worker checks: is this GitHub user a member of an org with an active team subscription?
- Keygen policy object per org, member licenses issued under it

## Identity Data Model

Canonical user identity: **GitHub User ID** (numeric, stable across username changes)

```
activation_record {
  github_user_id        // canonical identity
  github_login          // display only
  email                 // if available
  repo_url              // primary project repo
  repo_visibility       // public | private
  keygen_license_id     // license object reference
  tc_version_accepted   // version string
  tc_accepted_at        // timestamp
  xgd_version           // version at activation
  tier                  // free | pro | beta_pro
  status                // active | payment_at_risk | suspended
}
```

## Security Model

**Never shipped in client:**
- Jira API key
- Keygen API key
- Paddle webhook secret
- Any private key material

**In-client:**
- GitHub App installation token (scoped, short-lived, revocable)
- Activation JWT (signed by Worker, verified by Worker on refresh)
- XGD public key (for binary signature verification on update)

**Trust chain:**
- GitHub verifies user identity
- Worker verifies GitHub token with GitHub API
- Worker issues activation JWT signed with Worker private key
- Client presents JWT for all subsequent server calls
- Server verifies JWT signature — no round-trip to GitHub needed after activation
