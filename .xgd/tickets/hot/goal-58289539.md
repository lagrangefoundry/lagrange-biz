A ticket state tells you where the work actually is, all the way to the branch we deploy from.

**Not scheduled. Recorded on 2026-08-11 so the gaps are visible rather than rediscovered.** Surfaced while designing the On deck predicates (lagrange-framework/REQ-92), when "what does done mean" turned out to have three different answers.

## Gap 1 - nothing is tracked past reconcile

A feature is not done when it is reconciled. It is done when it has been through **regression** and landed in **stable** - and stable is what deployment ships from. Neither stage is a ticket state today. The free-coding lifecycle ends at `free_and_reconciled`, which is the end of that workflow, not the end of the road.

**Consequence for this map:** the accumulation register - the monotonic "what do I have now that I did not have in May" axis - cannot currently be measured correctly. Keyed on `free_and_reconciled` it counts work that has not passed regression and is not in stable, so it **overstates** what has been banked. REQ-92 implements that boundary anyway as the best available answer, explicitly marked provisional.

Related: goal-e4abb41b (regression lifecycle: event-driven, not timed), goal-215dd333 (Regression bugs - still empty after a week of heavy bug filing), xgd/GOAL-1 (Stable release: regression green end-to-end).

## Gap 2 - resync is invisible to ticket state

Develop cycles run in the background, unsupervised, cut from main and returned to main. Execution currently runs from `xgd-working` for fast feedback, so a feature built by the develop cycle only reaches working **after a resync**.

Develop ticket states are tracked. **Resync is not tracked as a ticket state change.** So a ticket can be complete in main and absent from the branch the operator is running, with nothing in its state saying so. Any view built on ticket state - including On deck - will be wrong about that ticket for as long as the gap lasts, and will not know it.

## Gap 3 - the develop cycle has no acceptance gate

The free-coding lifecycle has an explicit manual gate: `free_coded -> ready_to_reconcile` is the operator deciding a feature is done. It is the single most load-bearing signal in the whole model - it is what On deck uses to take a ticket off the board.

**The automated develop cycle has no equivalent.** Work arrives without anyone declaring it acceptable. That is not only a tracking gap: it means the two workflows carry different levels of assurance, while producing tickets that look alike downstream.

This matters most for the accountability claim. Both whitepapers argue that trust in AI-written software must be structural. An explicit human acceptance gate is exactly such a structure - and half the work does not pass through one.

## Why record rather than fix

The operator flagged these as awareness items on 2026-08-11, not work for the day. They are recorded because each one silently distorts a view built on ticket state, and a distortion nobody has written down gets rediscovered as a bug later.
