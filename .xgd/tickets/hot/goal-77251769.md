XGD runs on the new modular lagrange-framework components rather than on its own older copies.

Named by the operator on 2026-08-11 as importing the new modular framework components, which fixes several annoying bugs as a side effect.

## State 2026-08-18 - promoted to in_progress, three named pieces

Operator, 2026-08-18, on what the dashboard refactor actually consists of:

1. **Introduce the shell component.**
2. **Consolidate the Chat and Documents tabs** - goal-85b52724, already on the map, now attached here as a child rather than floating.
3. **Refactor the Intents tab with the new components.**

Neither (1) nor (3) has a ticket yet.

Moved from `concept` to `in_progress`. Two reasons, and the declared value was the stale one: roll-up already derived `in_progress` from REQ-781, and the operator has now named this as active work. Framework-side component tickets are landing against it - lagrange-framework/REQ-97 (goal map renders cross-project refs ID-first), REQ-98 (goal map exposes a `view_state` read op), BUG-33 (Calendar target-vs-event distinction, filed and fixed 08-18 in hours).

## The property that makes this safe

Operator: *"all disruptive but manageable changes because they can be run alongside the old code."*

Worth recording, because it is the same judgement as decision-9a363d88 - the access-control work became tractable the moment it could run beside the old path instead of replacing it in one move. That is now twice this shape has been chosen deliberately.

It also draws the line against the knowledge-management cutover (goal-74b33543), which explicitly **cannot** be run alongside the old code: REQ-775 deletes the static priming assembler. Two refactors, two risk profiles. Do not sequence them as if they were the same kind of thing.

## Why adopt rather than implement

The same move as xgd/REQ-781, which imports the new AI backend so Claude invocation runs through a single choke point with a declared permissions schema. Rather than implement a capability inside XGD legacy code, adopt the component that already has it. The permissions work was the first instance; the wider component import is the rest.

The bug-fixing is a genuine side effect rather than the motivation - a class of annoying defects disappears because the newer component does not have them. Fixes acquired rather than made. lagrange-framework/BUG-20 (unrecognised argument keys silently ignored) reaches a fix through this adoption.

**And a hazard, now demonstrated.** xgd/BUG-1163 was closed wont_fix because the fix belonged upstream: `xgd_source/dashboard/static/vendor/@lagrangefoundry/webui-goal-map/` is a verbatim vendored copy, and hand-editing it is exactly what caused BUG-950 (a prior hand-edit silently clobbered by the next re-vendor sync). Adoption means fixes go upstream and come back through `bin/vendor-webui-components`, every time. The more components XGD adopts, the more often that discipline is tested.
