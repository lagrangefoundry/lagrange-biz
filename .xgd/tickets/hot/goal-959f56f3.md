An operator can see, at a glance, what every AI session is permitted to do - and there is one place in the code where that is decided.

**Composition:** xgd/REQ-780 (Status tab tile listing Claude session roles and their permissions) is the visibility half; xgd/REQ-781 (Claude invocation: single choke point with a permissions schema for lagrangefoundry-ai) is the structural half. Both filed 2026-08-11 within a minute of each other, both draft.

## Why this became urgent on 2026-08-11

Lunch with the n=1 external user on 2026-08-10 (decision-fd14b9b9). Handing someone an agent that can write to your repositories is a different proposition from running it yourself, and the question "what is it actually allowed to do" had no answer in the product.

**This is the accountability claim, applied to XGD itself.** DOC-4 and DOC-8 both argue that trust in AI-written software has to be structural rather than promised. An AI development tool whose own permissions are invisible, and decided in several places, is hard to defend in a document making that argument. REQ-781 chooses a single choke point over scattered call sites precisely because a choke point can be audited.

Direct evidence the gap was real: on 2026-08-08 this assistant was refused a ticket create with "creating type request is not enabled for this session". Correct behaviour, but the operator could neither see what the session was permitted to do nor change it without reading code.

## Relationship to the Toolbox - adoption, not duplication

Recorded as depends_on goal-9cdf5f09. There is one permissions mechanism, not two.

lagrange-framework REQ-74 built the Toolbox as infrastructure. REQ-781 is **XGD adopting that infrastructure** - importing the new AI backend so Claude invocation runs through it, rather than implementing permission control inside XGD legacy code. Re-adoption rather than reinvention, and the reason the access-control work required a backend import before any permissions work could start.

Note that lagrange-framework REQ-75 is *not* on this path. It bridges to the framework ticket implementation, which XGD does not use.

State is aspiration: both tickets are filed and wanted, no work started, no date set. If this gates the n=1 onboarding on 2026-08-20 it needs a target date and should move to planned.
