How XGD manages what an LLM is permitted to do, rebuilt - not a visibility feature bolted onto the existing mechanism.

**Scope corrected 2026-08-13.** This goal was first recorded as "AI access control is transparent", which understated it badly. The operator: "it is much more than visibility - we have done a complete refactor of how access control from LLM is managed and integrated lagrange.ai as our backend component in the process. Big change, still working through it."

So this is two things at once: a rewrite of access control, and the adoption of lagrange.ai as XGD backend AI component. The second is the larger structural move - it is the route by which the Toolbox reaches XGD, and it replaces XGD legacy AI plumbing rather than sitting alongside it.

## Composition

- xgd/REQ-781 - Claude invocation: single choke point with permissions schema for lagrangefoundry-ai. **free_coding as of 2026-08-13 10:38.** The substantive work.
- xgd/REQ-780 - Status tab tile listing Claude session roles and their permissions. free_coded. The visibility half, which is now the small part.

Supporting work in framework, both free_coded: REQ-94 (lagrangefoundry.ai.permissions - model Claude Code native sandbox and network settings schema) and REQ-95 (Toolbox: multi-parameter scope axes, resolver fail-closed guard, manual-leak lint).

That is a coherent stack: framework declares the schema and the scope axes, XGD imports the backend, the Status tab renders what it permits.

## Why it mattered enough to do properly

Trust, with customers and beta testers rather than for the operator own benefit. Handing someone an agent that can write to their repositories raises a question the product could not previously answer.

It is also the accountability claim applied to XGD itself. DOC-4 and DOC-8 argue that trust in AI-written software must be structural rather than promised. A single choke point with a declared schema can be audited; permission decisions scattered across call sites cannot.
