This interface answers what should I work on next well enough to be used every morning without effort.

## Specification agreed 2026-08-08

### Split the view in two

**Top: On deck.** Renamed from ready frontier - the operator does not like that term. This is the working list.

**Bottom: Progress.** The provenance chart stays as a placeholder. Its real definition is deferred until On deck works. The current single pane tries to do both jobs and reads as noise.

### On deck: structure

A short list of workstreams. Under each, its live leaves. Beside each, its target date.

    XGD packaging v1 - install tool          2026-08-20   12 days
       xgd/GOAL-2      Packaging with an update path        planned
       xgd/REQ-754     xgd update command                   draft
       xgd/REQ-755     ./bin/build release-packaging        draft
       xgd/REQ-756     ./bin/deploy release-publishing      draft

    Site builder                             2026-08-31   23 days
       1stcontact/GOAL-16   Web editor                      in_progress
       1stcontact/GOAL-17   Editor chat                     concept

Leaves answer what do I do next. The workstream header answers why. The date answers how long have I got.

### On deck: rules

1. **Workstreams are marked, not derived.** A new boolean goal field. Expected population 5-8; it changes slowly.
2. **Leaves are derived.** Under each marked workstream, show descendants with no live children, whose state is planned or in_progress, and whose depends_on all resolve to realized.
3. **Resolve cross-project refs.** Fetch title and state for every ticket:// child. Resolution by uid works today; only enumeration (list/query/search) fails across a store boundary. The current code does not resolve, which is why cross-project parents masquerade as leaves.
4. **Sort by date proximity.** Dated workstreams first, nearest deadline at top; undated after.
5. **Strip the authority.** Render 1stcontact/GOAL-16, not ticket://lagrangefoundry/1stcontact/GOAL-16. Every project is under lagrangefoundry, so the prefix is pure cost. DOC-19 section 7 explicitly permits splitting the authority off the front for display.

### Why marked rather than derived

Measured against the map on 2026-08-08, grouping every live leaf under its immediate parent returns roughly 16 groups and 70 leaves - the same noise, indented. The operator daily resolution is five workstreams: XGD bugs, XGD packaging v1, the site builder, this experience, and the chat infrastructure beneath it. No derivation produces that set, because the distinguishing property is that the operator chose them.

Note the resolution mismatch this exposes: XGD bugs is one item to the operator but six goals in the map (Reconcile, Resync, Development, Regression, Ticketing, Dashboard). Six is right for filing, one is right for the daily list. Marking resolves this - mark the parent, not the six.

### Later: derive marks from open intent tabs

The operator already keeps an intent tab open per active ticket and closes it when done, and describes this as a workspace affordance they could not function without. That is a hand-maintained on-deck list that costs nothing extra. Sourcing marks from open intents would make the list self-maintaining. Deferred - it needs the intent tab to expose data - but it is the right end state, and the manual flag should be designed so it can later be overridden by that source.

## Other known defects

**No way to express a standing goal.** The ladder assumes goals terminate. XGD Remove friction and the workflow bug goals never complete; they can never reach realized, so they contribute nothing to accumulation and sit on the list forever.

**Roll-up ignores cross-project children.** Same root cause as rule 3. Two realized 1stcontact goals wired under XGD site live on 2026-08-08 did not move its derived state. Three of the four standing disagreements on this map are this, not drift.
